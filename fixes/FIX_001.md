### 1. Findings that matter most

The delivery sequence, clarified by the user during the final review, is:

1. **Now: establish the first successful E2E baseline.** Run the existing base
   case through the configured real LLM, engine validation and publication to
   produce the first official `spec.md`, then complete rubric evaluation of
   that actual output. “Official” means engine-published through the production
   workflow; it does not mean a prewritten expected answer.
2. **After that baseline succeeds: exercise and compare changes.** Use the
   harness to benchmark engine code and prompt changes against the retained
   baseline, including controlled A/B runs and repeated executions to measure
   model variation.

The current failed runs are useful baseline-development diagnostics. They
identify defects and exercise code and prompts, but contain no completed output
to establish a specification-quality baseline. Building comparison machinery is
not a prerequisite for getting this first E2E case to complete. The immediate
remediation should address the shared failures below and validate that outcome.

The repeated failures reveal an incomplete **proposal → validation → guided
correction** contract. The engine rejects invalid data, but it does not
consistently explain repairable candidate failures back to the model. One
shared correction mechanism also supplies an example that violates a downstream
validator. These are concrete engine issues, not merely a model failing to obey
a correctly communicated, complete contract.

The retained evidence establishes:

1. **Correction guidance can demonstrate invalid domain data.** The generic
   schema example generator produces a retained claim that references itself.
   The latest run eventually returns that same invalid relationship pattern.
2. **Some enforced rules are absent from model-facing guidance.** The model is
   shown a response schema, but that schema and the initial prompt do not
   communicate important relationship and coverage constraints.
3. **Schema-valid candidate errors often terminate instead of receiving guided
   repair.** Reconciliation errors lose their precise cause at the application
   boundary and go directly to `end.failed`.
4. **The model is asked to reproduce some facts the engine can derive exactly.**
   This adds unnecessary fields and opportunities for inconsistency.
5. **A negative semantic review can stop execution without identifying an
   actionable missing decision or producing a clarification form.**
6. **The harness has a real call-attribution defect and incomplete failure
   summaries.** Raw evidence generally survives, but some events mix the current
   repair response with the previous candidate's origin.
7. **Native structured output did not work reliably in the observed provider,
   model and schema combination.** It is not an established remedy here.

Across **11 retained runs**, there were **132 recorded provider attempts**,
**421,345 accounted tokens**, **zero published specifications** and **zero rubric
evaluations**. Every model assignment was still preparing source evidence:
74 extraction, 55 reconciliation, two extraction repair and one pre-generation
support review. **No retained run reached the actual specification-generation
model request.** Therefore, these runs cannot establish the quality of a
generated specification, plan, task list or implementation.

### 4. Detailed causes and ownership

#### 4.1 The shared protocol example contradicts downstream validation

The latest global reconciliation starts at R11 call 11. Its retries include
this engine-generated `schema_example`:

```json
{
  "claim_id": {"ordinal": 1},
  "disposition": "retained",
  "related_claim_ids": [{"ordinal": 1}]
}
```

That example is structurally valid under the selected JSON schema. It violates
two rules in the canonical
[claim-disposition validator](../src/actions/reference/validate_reference_claim_dispositions.zig),
lines 21–37: a claim cannot relate to itself, and a retained claim must have no
related claims.

The defect is in the shared
[example generator](../src/domain/model_protocol_retry.zig), lines 28–56. It chooses
the first enum (`retained`), minimum integer (`1`), and one array item even when
the array may be empty. Structural schema information alone cannot prove that
this combination is valid under domain relationships.

The recorded sequence is precise:

| 12–14 | Empty relationship arrays; other JSON problems remain | Retained claim 1 references itself |
| 15 | First self-references, 1→1 and 2→2 | Same invalid example |
| 16–18 | Self-references remain; JSON still fails | Same invalid example |
| 19 | JSON/schema finally passes; self-references remain | Same invalid example |

**Established:** invalid illustrative guidance preceded the regression and

or that removing it alone would have completed the workflow. Calling example
values placeholders does not make the illustrated relationship valid.

This matters across the engine: a first enum value plus minimum IDs cannot
reliably illustrate task dependencies, plan relationships or authorization-bound
records either. Adding a special case for retained claims would leave the
shared defect intact.

#### 4.2 The response shape was supplied; the complete acceptance rules were not

The actual initial [extraction request](../zig-out/e2e-spec/2026-09-12T08-21-11Z-db6e32272690b41d790fdf5044c10fa3/evidence/generation/call-000001/request.json)
and [global reconciliation request](../zig-out/e2e-spec/2026-09-12T08-21-11Z-db6e32272690b41d790fdf5044c10fa3/evidence/generation/call-000011/request.json)
include the task prompt, universal JSON instruction, complete selected schema
and input evidence. Missing initial JSON-shape guidance is therefore not an
explanation for these runs.

However, the initial [reconciliation prompt](../design/workflows/spec/reconciliation.prompt.md)
only requests one disposition per claim and cited signals/conflicts. The
[input producer](../src/domain/reference_model_input.zig), lines 42–55, supplies
evidence and IDs. The [schema](../design/workflows/spec/reconciliation.schema.json),
lines 339–369, permits a disposition enum with a generic relationship array.
None communicates the complete dependent constraints enforced later:

- `retained`: zero related claims; `duplicate`: exactly one;
  `superseded`/`conflicting`: at least one.
- No self-relations; appropriate compatible claim kinds; symmetric conflicts;
  acyclic duplicate/supersession relationships.
- Signals must cover retained claims and non-conflicting preserved tokens, as
  enforced in [validate_reference_signal_proposals.zig](../src/actions/reference/validate_reference_signal_proposals.zig),
  lines 32–34.

The model is consequently being judged against rules that are more precise
than its supplied instructions. Deterministic rejection is correct; treating
every such rejection as a terminal operational failure is not a complete
implementation of guided proposal correction.

The earlier syntax failures are still real. In R07, call 3 omitted
`/statements/0/content/kind`, despite the schema. Later responses repeatedly put
subsequent statements' keys inside one statement object, creating duplicate
fields. See [call 3](../zig-out/e2e-spec/2026-09-12T07-23-28Z-088179a795c62a52ae07b79e1bebf107/evidence/generation/call-000003/model_output.txt)
and [call 12 correction](../zig-out/e2e-spec/2026-09-12T07-23-28Z-088179a795c62a52ae07b79e1bebf107/evidence/generation/call-000012/context.json).
More domain guidance alone cannot be claimed to fix malformed JSON.

#### 4.3 Expected candidate invalidity is collapsed into operational failure

After JSON/schema success, the engine runs domain validators. Several
reconciliation validators return `InvalidReferenceReconciliation` for different
candidate mistakes and also for context/invariant failures. The generic
application binding catches these as `OperationExecutionFailed` in
[reference_reconciliation_workflow.zig](../src/application/reference_reconciliation_workflow.zig),
lines 108–135. The [workflow](../design/workflows/spec.workflow.yaml), lines 384–415,
then sends summary/disposition/signal/conflict failures directly to `end.failed`.

This explains R04, R05 and R11: the model can produce schema-valid data, but the
engine does not return the actual domain rule and authorized correction scope
to it. In R11, there is no request after call 19 explaining that retained
relationships must be empty.

The problem extends beyond one reconciliation rule. Extraction text rejection,
reference-claim invalidity and specification-coverage invalidity also have
terminal transitions in the current YAML. These branches must be classified:
some are repairable candidate errors; others may require authority or environment
intervention. They must not all become retries.

The existing [candidate diagnostic union](../src/domain/candidate_validation_diagnostic.zig),
lines 5–20, covers classifications, source selections and specification repair,
but not reconciliation. This is why an important failed rule can be absent from
the structured report despite the raw response being retained.

The architectural building blocks already exist:
[atomic_repair.zig](../src/domain/atomic_repair.zig) supplies owner/revision/target/
old-value authorization and compare-and-swap checks;
[reference_extraction_repair.zig](../src/domain/reference_extraction_repair.zig)
and [specification_repair.zig](../src/domain/specification_repair.zig) reuse them.
A second repair engine is unnecessary.

The source review also identifies defects in the existing specification repair
boundary, which none of the retained runs reached:

| Static finding | Evidence and implication |
| --- | --- |
| Failure discovery is duplicated | [specification_generation.zig](../src/domain/specification_generation.zig), lines 55–83, and [specification_repair.zig](../src/domain/specification_repair.zig), lines 16–44, repeat unit traversal, record-kind checks and normalized duplicate-content rejection. Shared provenance helpers remain shared, but the authorizer independently rediscovers higher-level failures. Rules can drift between rejection and authorization. |
| Context failure can resemble repairable provenance | [specification_provenance.zig](../src/domain/specification_provenance.zig), lines 15–18, uses `InvalidSpecification` for inconsistent reference-state/corpus binding. | Some repair targets are broader than the defect | Specification repair targets and replacements, lines 8–11 and 80–89, expose an entire attributed value or record. Narrower targets are needed where those parts are independently valid; record-level repair remains appropriate for an inseparable defect. |

The validator should discover the failure once and retain its native typed
rejection. The authorizer consumes that rejection and current candidate to
verify association, revision and permissible replacement scope. Harness JSON
is a diagnostic projection and must never become repair authority.

#### 4.7 Native mode and retry counts are not demonstrated solutions

R09 and R10 submitted native schema constraints but received malformed prefixes
such as `{"{ "kind":...`. Each had 28 recorded JSON rejections and a final raw
response that did not reach decoding before the budget stop. The malformed
prefix is already in the provider response; it is not introduced by the engine's
candidate decoder.

Retained [simple-object probes](../zig-out/native-schema-probe),
[variant probes](../zig-out/native-schema-variant-probe) and
[enum-tag probes](../zig-out/native-schema-enum-probe) reproduce failures with small
alternatives outside the workflow while some simple schemas succeed. These are
diagnostic calls, not E2E evidence. They do not establish that native mode fails
for every model or schema, or identify the provider's internal implementation
defect.

The supported conclusion is narrower: **native mode is not a validated quality
improvement for this configured combination**. Changing modes, changing model,
adding prompt prose or increasing retries cannot be claimed to solve the
workflow without evidence. Current prompt-only defaults preserve explicit
configuration; a silent fallback would obscure the actual tested path.

Current protocol retries already reuse the original task/input/schema plus the
latest rejected response and diagnostic. They do not accumulate the entire
correction history or have a hidden retry engine. Existing local operation
limits and the execution-wide token ledger own repetition. More calls cannot
repair an undisclosed rule or make a misleading example valid.

#### 4.8 Schema compatibility needs independent conformance evidence

The source schema, compiled schema, complete model-facing projection and native
provider grammar derive from one structural authority. Request preparation
retains that schema association; runtime validation uses it. These layers,
strict decoding and domain validation serve different responsibilities and
should remain distinct. Compact serialization already exists.

Native candidate types are maintained separately, however. The
[schema compiler](../src/domain/model_result_schema.zig), line 210 onward, permits
optional properties, while [model_candidate_json.zig](../src/domain/model_candidate_json.zig),
lines 49–64, requires every native struct field. Nullable does not mean
omittable. No active mismatch was established in the current five Specify
schemas: they require all declared properties, contain no null nodes, and use
integer bounds `1..4294967295`. Exact integer decimal/exponent spellings already
have shared handling and tests. Optionality and narrower native numeric types
are compatibility risks to cover, not diagnosed causes of the retained runs.

The [schema/native conformance test](../src/model_candidate_json_test.zig), lines
69–96, uses the production example generator. It visits selected definitions
and root alternatives, but nested `oneOf` nodes take only their first branch;
the test never applies domain validation. That explains a concrete coverage
limit: a retained-self-reference example can pass those structural checks.
Removing the generator must replace this coverage and the example-dependent
assertions in [model_payload_schema_test.zig](../src/model_payload_schema_test.zig),
not remove the conformance obligation.

Use independently specified schema/native cases plus domain-valid and invalid
cases under retained engine inputs. Cover every nested alternative, selected
definition, empty object, applicable omission/null distinction, numeric boundary
and unknown field. Representative tests establish bounded evidence, not a proof
that every possible payload decodes. No new schema framework is needed.

#### 4.9 Runtime assembly and publication need distinct evidence

[Production composition](../src/composition/root.zig), lines 87–127, and
[E2E invocation](../test/harness/e2e/invoke.zig), lines 9–61, independently assemble
substantially the same native operations, adapters, provider runtime and clock.
This is confirmed wiring duplication and a drift risk; no wiring divergence
has been established as a cause of the retained failures. The harness still
uses the production invocation, provider, runner, validators and workflow.

A shared assembly boundary is a scoped follow-up improvement. Preserve narrow
inputs for the isolated project, test credential source, runtime controls and
observation; keep fixture and publication checks in the harness. Do not turn
this into a service locator or make broad composition refactoring a prerequisite
for the first baseline without a demonstrated blocking divergence.

An in-process success also does not exercise every shipped CLI argument,
environment or exit path. Preserve the existing launcher and clean native
packaging checks; they are separate evidence, not absent functionality.

Publication has a further boundary worth preserving. The
[output adapter](../src/adapters/filesystem/workflow_output.zig) replaces files
sequentially; earlier writes may remain after a later failure. The
[output contract](../src/domain/workflow_output.zig), lines 37–39, requires
completion state last. The [harness oracle](../test/harness/e2e/oracle.zig) requires
successful engine-observed publication and exact agreement for all expected
artifacts. A `spec.md` file alone therefore cannot establish the baseline.
Retain partial-write, state-ordering and fresh-rerun failure checks under design
§25/ADR 0009; do not introduce rollback, checkpoints or another transaction
framework.

### 5. Why the visible failure keeps changing

The retained runs reach different rejection points because they produce
different candidates and have different implemented correction capabilities.
Fixing a JSON boundary can let a later relationship or authority defect become
visible. The shared invalid example also demonstrates how a syntax-correction
request can be accompanied by a regression in domain values.

R04, R05, R06, R07 and R11 have identical captured input/workflow bytes but
different outcomes. Engine changes prevent treating that as an isolated model
experiment. These observations remain useful for locating blockers on the path
to the first successful specification; one passing parser test or one later
failure step does not establish completion. Current evidence supports multiple
interacting failure classes, not one oscillating JSON bug.

The test should assess the whole engine's ability to turn variable, untrusted
proposals into validated output. It should not require the model to produce
one prewritten answer. Determinism means the same accepted structured payload
renders the same bytes; it does not mean all acceptable paraphrases or model
responses must be identical.

### C14-1 — High: whole-chunk replacement is not established as atomic

The previous recommendation in IMP_001 called replacement of all claims and token
classifications in one source chunk the smallest decision. That is unsafe as a
general authorization: a partially correct chunk can contain independent valid
claims and classifications. [§22.1](../design/contracts/22-repair.md#221-definition-of-atomic)
and §22.3 preserve unrelated valid units and restrict coupled replacements to
predeclared inseparable members. Revalidation of a dependent unit is not authority
to replace its semantic content.

Current [extraction repair](../src/domain/reference_extraction_repair.zig) selects a
classification collection, one citation or an empty citation collection;
[extraction text repair](../src/domain/reference_extraction_text_repair.zig) selects
an individual text value. Neither inserts lost semantic claims after reconciliation.
A missing independent claim may require insertion; a wrong classification may
require an existing replacement; an incorrect `no_feature_claim` result may require
replacement of that discriminated outcome. Their dependency closures differ.

**Required decision:** authorize only a validated minimal target at the owning
candidate boundary. Whole-chunk replacement is permissible only if an accepted
contract demonstrates inseparability; it cannot be the default or an escalation
after narrower repair fails. The refined proposal is in
[IMP_001](IMP_001.md#decision-required-before-automatic-extraction-repair).

### C14-2 — High: omission evidence does not locate the defective producer

[Source-preservation review](../design/workflows/spec.workflow.yaml) runs after
extraction and reconciliation. A missing behavior can therefore originate in
either operation. Current findings in
[specification_support](../src/domain/specification_support.zig) retain requirement
ordinal, decision, claim selection, source IDs and prose. The corresponding
[persisted review evidence](../src/domain/required_authority.zig) does not name an
exact raw claim, chunk, source span, classification or defective producer.

The [evidence packet](../src/domain/model_evidence.zig) already exposes source/chunk/
span associations, but no typed result selects and validates that loss location.
A source ID cannot uniquely locate an omission in a multi-chunk document. Sending
every source-preservation omission back to extraction could duplicate a correctly
extracted claim whose meaning was lost in reconciliation.

**Required contract:** retain source-backed semantic evidence and validate a unique
loss boundary/target before authorizing repair. Domain owners contribute these
typed facts through the shared authority/repair contracts; neither a support
reviewer nor a workflow caller chooses a continuation. Missing, ambiguous, foreign
or stale targets stop explicitly. Do not infer targets from prose, filenames or
the Hello World fixture. Genuine source-authority gaps retain clarification or
upstream rework; malformed review records retain their own mechanical correction.

## 29. Architecture brittleness assessment

**Conclusion:** the system has strong rejection safeguards, but successful

across repeated transformations. Correct rejection does not make that contract
reliable. There are also concrete composition problems in retries and dependency
renewal. Calling every incident model nonconformance understates the architecture's
contribution; weakening validation would conceal it.

### Model-facing constraints lag behind native knowledge

The [evidence owner](../src/domain/specification_support_evidence.zig) already
determines eligible claims, positive evidence minima, exact sets and candidate
provenance. The [selected schema](../design/workflows/spec/support.schema.json)
admits empty evidence, arbitrary positive ordinals and incomplete/duplicate review

These are not contradictory authorities, but the model must reconstruct their
intersection from the packet. R28's empty repair passes the structural shape while
violating the supplied `claim_required` rule.

[Batch schema selection](../src/domain/specification_support.zig) exposes another
residual choice: one genuine entity-applicability task selects `review_applicability`

### Repeated semantic transformations multiply failure opportunities

The [canonical partition owner](../src/domain/reference_reconciliation_partition.zig)
creates within-source, cross-source and global levels even for one source with one
group. R28's three reconciliation requests each required correction: six provider

Pre-generation review asks whether source meaning can support specification fields;
post-generation review checks actual candidate support. Those are distinct
responsibilities. The observed weakness is their application to meaning, not proof
that a gate should be deleted. A model-supported negative finding can be mechanically
valid and still mistaken. It must not be flipped by repair code to force publication.
Likewise, genuine business gaps remain clarifications and policy conflicts retain
their approved stage ownership.

### Recovery is not yet compositional

**New static finding — source/principle review consumes shared retry allowance.**
The [post-generation call](../design/workflows/spec.workflow.yaml) enters
`review-support` with `retry-limit: 1`. After accepted source review,
`advance.more -> input` runs principle assessment through the same compiled
`model-request`/`account` nodes. The
[runner](../src/application/workflow_pipeline_runner.zig) counts visits per compiled
step for the whole invocation; new request identity and transport retirement do
not reset that count. Protocol correction also returns to that same account node.

With supported post-generation content and nonempty selected principle chunks:

1. Source review's initial call consumes account execution 1.
2. One protocol correction, even when successful, consumes execution 2.
3. Principle review's initial call encounters `2 > retry-limit 1` and is rejected
   before inference.

Even two clean reviews consume the entire allowance. The atomic-repair account is
also shared across phases. This is a concrete composition defect established by
control-flow/counter inspection, **not a newly executed regression or R28's cause**.
Current principle fixtures do not combine successful source correction with policy
assessment. Sharing implementation is appropriate; unintentionally sharing
recovery allowance changes behavior. [ADR 0005](../design/decisions/0005-workflow-defined-operations.md)
and [§12.3](../design/contracts/12-model-boundary.md#123-provider-neutral-response-envelope)
own per-operation-instance limits. A fix must preserve explicit retry authority,
not silently reset counters or increase this caller's limit.

confirms the collision with a failing combined regression and delivers the approved

**Reviewed 18 September 2026; analysis and `fixes/*` updates only.** This review
traces the current compiler, registered bindings, runner, request lifetime,
response owners, retry/usage accounting and downstream consumers. It evaluates
consolidation across arbitrary workflows, not a Specify-only execution shortcut.

**Conclusion:** full request orchestration can reuse the existing runner, but the
current runtime has no registered composite-child contract. Introducing one is a
cross-cutting architecture change. It is unnecessary merely to fit the next review
composition: a cohesive pure response-admission operation projects **498** expanded

withdrawn as the recommended next step.

### What is repeated, and what consolidation would actually reduce

[workflow](../design/workflows/spec.workflow.yaml) and the retained independent-review
proposal (`.zig-cache/chunk13-distinct-reviews.workflow.yaml`):

composite operation does not make it admissible. The
[execution limit](../src/domain/workflow_compilation.zig) is also distinct: it is
derived from graph size and declared retry limits, and bounds runtime visits.

### Existing ownership and the missing composite boundary

- The [subgraph compiler](../src/domain/workflow_subgraphs.zig) expands calls into
  ordinary operations with deterministic call-path identities. The
  [graph validator](../src/actions/workflow/validate_compiled_workflow_graphs.zig)
  then checks contracts, lifecycle, capabilities, gates, reachability, bounded
  cycles and dataflow. Different incoming data sets cannot be merged simply
  because two branches use the same publication implementation.
- The [generic orchestrator](../src/application/workflow_engine_orchestrator.zig)
  follows compiled transitions through typed runner-owned bindings. The
  [runner](../src/application/workflow_pipeline_runner.zig) guards each child,
  resolves current authority, enforces retries, invokes its binding and validates
  and applies its delta. These responsibilities already have an owner.
- [Registered bindings](../src/ports/workflow_operation_registry.zig) return one
  candidate delta. They have no child-binding interface. The
  [binding inspector](../src/application/workflow_operation_binding.zig) rejects
  arbitrary callbacks and capability bags. Passing the runner or registry into
  an ordinary request action would violate this boundary.
- Request identity/preparation, provider authorization/lifecycle, observation
  validation, protocol correction and response admission already have separate
  owners. A private request executor would duplicate their coordination authority;
  a new model agent would not address the static graph or retry collision.

### If full runner-owned request orchestration is pursued

The least disruptive representation is to retain the existing compiler-owned
`call` structure, with bounded call/return frames in the capability-free graph
walker and the existing runner invoking every detailed child. YAML remains the
sole topology authority; no second dispatcher or request-specific execution loop
is needed. This would amend ADR 0013's requirement to flatten before execution.

A registered native request coordinator is another possibility, but additionally
moves lifecycle order/branches from YAML into a native composite contract. It
would require extending the same registered-node/compiled-node contract with
typed runner-owned children. If selected, remove the superseded YAML lifecycle
body; do not maintain two descriptions of its transitions. Neither form belongs
inside an action. Both need the following architecture-wide guarantees:

1. **Complete compilation and selection.** Validate every child and exit, including
   nested calls, recursion rejection, parameter forwarding, failure propagation,
   data availability, invalidation and gate effects. Derive or validate composite
   summaries against the child graph; a hand-maintained parent capability list
   cannot replace child checks. Update registry cloning/equality, captured-resource
   binding and provider-requirement discovery together. Parent selection must bind
   the exact current child structure, resources and parameters.
2. **Stable identities and independent allowances.** Identify each child by its
   static complete call path and local operation identity, preserving
   [retry authority](../src/domain/workflow_retry.zig). Source and principle
   initial/repair sites must differ. Reusing one body does not reuse its caller's
   counter. Re-entering a call site does not replenish its allowance. Request
   ordinals and provider-attempt IDs retain their existing distinct purposes;
   no counter keys come from model content, slot, prompt or review-mode strings.
   Protocol correction retains its logical request and accounting site; semantic
   repair remains a separately authorized request.
3. **One runner and shared accounting.** Route every child through existing
   guards, authorization, delta application, cancellation, deadlines, telemetry
   and failure barriers. Preserve typed execution rejections, not merely a generic
   failed status. Share the invocation-wide visit/retry/token accounting state
   across call frames. Keep recursion, call depth, logical expansion and runtime
   visits explicitly bounded; storage compression cannot reset or hide them.
4. **Preserve effects already performed.**
   [Actual usage](../src/application/workflow_model_invocation.zig) is reconciled
   immediately after a provider attempt, before response publication or later
   cancellation. Children therefore cannot be accumulated into one supposedly
   atomic parent delta. Coordinate already-applied child results; never reapply
   them, charge parent and child, discard an earlier charge, fabricate unknown
   usage or re-invoke a provider during cleanup. Pure validation remains possible
   after model-budget exhaustion.
5. **Retain exact evidence and lifetime.** Keep the selected schema, request owner,
   original packet, precise diagnostics and latest rejected response through
   correction. Native domain consumption and full-candidate validation still
   follow shape admission. [Transport retirement](../src/domain/model_transport.zig)
   stays after consumption; moving it into request completion would destroy data
   the consumer needs. No call-frame store, checkpoint or rerun replay is added.
   Existing source/policy freshness and chunk 14's unresolved renewal rule stand.
6. **Keep authoring and domain responsibilities separate.** Slot, prompt, schema,
   native selection, controls, timeout, retry allowance and outcome bindings remain
   explicit at their existing owners. Domain review, repair authorization/merge,
   clarification and publication stay outside transport coordination. Preserve
   detailed operations for workflows requiring them, while removing superseded
   wrapper paths. No hidden defaults or longer prompts are necessary.

This affects the compiler/registry, graph walker, child bindings, runner identity
and bounds, provider preflight and observability. It requires conformance between
detailed and composite execution, including unrelated workflows, failure at each
child, cancellation after charged inference, allocation cleanup, stale/foreign
evidence, exact limits, recursive/invalid graphs and repeated use. Per-child
provenance and barriers must survive; an optional parent trace cannot substitute
for them. Full verification and native packaging evidence are required.

### Smaller next change: pure response admission

[Envelope decoding](../src/domain/model_envelope.zig) and
[payload-schema validation](../src/domain/model_payload_schema.zig) form one
cohesive responsibility: admit a validated response's syntax and selected shape.
Both are pure; schema evidence borrows the decoded candidate. Refactoring their
existing application result owners lets detailed operations and one consolidated
operation share construction without actions calling actions or duplicate parsing.

Publish the existing two sealed results together, with payload evidence retaining
the exact envelope and its observation. Preserve separate malformed-JSON and
schema diagnostics, provider stop/failure/cancellation outcomes, ownership cleanup
and current-authority dependencies. The shared
[contract predicate](../src/domain/workflow_model_invocation.zig) currently requires
one response output; approval must permit exactly this pair, retaining the other
restrictions. This is a focused ADR 0012/catalogue amendment, not implicit authority
from the earlier preparation approval.

Replacing two adjacent pure operations with one saves one real operation at each
request site: **517 − 19 = 498** for independent reviews. Applying it only to the
shipped graph would give 461 and leave the retry collision unresolved. The pair
has one delta-application/cancellation boundary instead of two; these pure steps
emit no telemetry facts. Request/provider identities, retries and usage must
remain unchanged for equivalent response trajectories. The ownership/frontier and
failure tests in the linked plan must prove that tradeoff. No nested runtime,
new response format, prompt/schema change or graph-capacity increase is required.

**Disposition:** propose pure response admission plus distinct review/repair call
sites first. Defer runtime orchestration until it has a demonstrated benefit beyond
hiding expanded counts, and then use the shared compiler/runner contract above.
Neither approach repairs model semantics or resolves chunk 14's lineage conflict.
Chunk 13 remains open; published/scored live readiness remains unproven.

Counts above come from read-only structural inspection, not a new compiler/test
run. The last implementation check remains **120/124 steps; 1,483/1,485 tests**, with
the known chunk 14 case failing in two suites. This assessment runs no tests or
model calls and changes no code, design, YAML, prompts or schemas.

## 33. Per-workflow idempotent information stack assessment

**User-directed requirement, 18 September 2026; original analysis below.**
The [subsequent implementation](IMP_001.md#shared-workflow-information-and-r30-delivery)
records delivered contracts, regression evidence and remaining limits. Create a common place for workflow information, make placement idempotent,
and create a fresh instance for every workflow execution. Here, “stack” means an
execution-scoped typed information store. Reading a fact must not remove it as a
destructive last-in-first-out `pop` would. Insertion order never decides authority.

### Existing owner and actual gap

The required owner already exists. [`engine_invocation`](../src/composition/engine_invocation.zig)
creates a [`Runner`](../src/application/workflow_pipeline_runner.zig) for the selected
workflow, and its initializer creates an empty
[`PipelineEnvelope`](../src/application/pipeline_envelope.zig). That envelope owns
typed immutable values, restricted read views, validated replacements, generations
and dependency lineage. This implements the single accumulated-data owner required
by [design §6](../design/contracts/06-pipeline-nodes.md).

Before this delivery, it did **not** provide general idempotent information placement:

- A repeated write to an occupied key rejects; an authorized replacement advances
  its generation even when the payload text is unchanged.
- Values replaced or invalidated in the envelope are released unless another
  existing owner retains them. There is no general immutable record history.
- Origins identify a producer and the generation assigned after application.
  There is no generic identity for a particular producer invocation before placement.
- Opaque native values have sealed owners, not a generic semantic equality operation.

Consequently, the change needs an explicit insertion/identity/lifetime contract at
this owner. A second property bag, global message bus or parallel evidence registry
would leave these gaps and introduce competing ownership.

### Idempotence must preserve execution semantics

Idempotence applies to recording the **same information occurrence**, not to
executing an operation again. The same declared record, producer occurrence,
payload and provenance placed twice must yield one retained entry and no second
generation, retry increment or token charge. Reusing that identity with different
facts must reject. A later repair, source revision or provider attempt is distinct,
even if its text equals an earlier result.

This distinction is already important: the
[lineage regression](../src/pipeline_data_test.zig) correctly invalidates a gate
after a same-content source replacement. The
[token ledger](../src/domain/workflow_token_accounting.zig) rejects repeated
reconciliation of one provider operation. Neither safeguard should be weakened
to make storage appear idempotent. A record receipt proves placement only;
subsequent accounting, telemetry, validation or publication can still fail.

### Scope, responsibility and expected benefit

| Concern | Required boundary |
| --- | --- |
| Lifetime | One fresh instance for each top-level workflow invocation, including another invocation of the same workflow and feature. Retries and compiled child subgraphs share that instance. |
| Storage | The existing envelope owns typed record placement and lifetime. Native owners retain their payloads; declared projections reference those owners without creating competing facts. |
| Authority | Current values and gates remain distinct from retained observations. Historical/rejected data cannot satisfy a current requirement or be restored by duplicate insertion. |
| Validation | Existing domain/provider validators determine admissibility and freshness. Storage verifies its closed insertion contract; it does not judge business meaning. |
| Execution | The runner applies deltas and controls lifecycle/accounting. Orchestrators coordinate; actions return declared outputs and receive bounded immutable views. |
| Model context | Existing packet builders select the relevant facts. The whole stack is never automatically appended to prompts. |
| Completion | Terminal reports take owned projections before teardown. Fresh executions cannot resume a stack; persisted predecessor/clarification input is revalidated through existing gates. |

The `current`, `captured` and `execution_control` schema distinctions describe
authority dependencies; `captured` is not an instruction to archive every old
payload. Retention must be explicit and bounded by the execution's native
contracts. Share existing immutable owners and retain only the declared information
needed for consumers and reports, rather than every intermediate workflow snapshot.

This can prevent duplicate placement, lost references and inconsistent consumer
copies. R30 still requires its provider normalization and retry-report fixes:
information discarded before placement cannot be recovered by the stack. UTC's
semantic omission also remains a source-review/conformance concern; the original
text already reached the model. The stack neither creates a missing answer nor
authorizes a new retry policy.

**Disposition:** [contract, implementation order and acceptance tests](IMP_001.md#per-workflow-idempotent-information-stack--implementation-plan).
The original plan established the requested scope without changing code. The
[subsequent delivery](IMP_001.md#shared-workflow-information-and-r30-delivery)
implements it with focused governing contract amendments. It preserves ADR 0009
and leaves Chunk 14's lineage decision and live-run approval separate.

### Why global reconciliation exists—and what should be sliced

Within-source summaries do not establish relationships across all claims. Global
reconciliation owns duplicates, supersession, conflicts, supported signals and exact
coverage. Individually well-shaped slices can still contradict one another, select
incompatible claims, omit obligations or form relationship cycles. Those checks remain.

The current YAML asks one LLM call to generate `claim_dispositions`, `signals` and
`conflicts` together. Only extraction currently uses configured composition. The
user's direction is to generate smaller logical slices, admit and retain each, then
assemble without a prompt and reconcile/check the assembled candidate. Final checking
must not regenerate accepted slices. Semantic relationship judgments still need
bounded model proposals; native code owns mechanically decidable checks and repair
authorization. Correct JSON is not proof of complete or nonconflicting meaning.

Start the design from those three logical collections, with projections dependent
on dispositions where required. Reuse the existing composition/compiler/runner and
native relationship validators. This is **not configuration-only today**:
composition resolves the resource root (currently `summary`), while ordinary global
requests select a named definition; reconciliation collection also expects one
provider response/origin. The shared binding and native provenance handoff must be
completed together before switching the workflow. Copying a global schema or
pretending assembled JSON came from one provider call would create duplicate authority.
Whole-array parts still contain nested records; any later item-level slicing requires
the finite identity/coverage/order contract already reserved by ADR 0016.

### 3. Confirmed repair defects

#### F1 — Authorization does not consistently establish a feasible target

**Effect:** the engine can spend a bounded repair operation on a field for which
no permitted replacement can satisfy the frozen mechanical dependencies.

[Content validation](../src/domain/reference_reconciliation_validation.zig),
lines 29–56, permits model content only when every selected claim has that model
kind. Preserved-token content requires exactly one matching token claim.
[Authorization](../src/domain/reference_reconciliation_repair.zig), lines 72–78
and 137–141, maps a content rejection directly to statement/signal content repair.
It freezes the selected claim list without retaining whether any content is valid
for that list. R15 selected a business claim and a token claim together. No member
of the content union can satisfy that combination. Mixed model kinds and multiple
token claims expose the same defect in both summary and signal consumers.

There are independently observable siblings beyond content compatibility:

- [Conflict validation](../src/actions/reference/validate_reference_conflict_proposals.zig),
  lines 22–27, requires at least two mutually conflicting claims. An extra conflict
  record with all dispositions retained has no valid selection. Authorization
  nevertheless chooses `conflict_selection` at line 158.
- [Signal validation](../src/actions/reference/validate_reference_signal_proposals.zig),
  lines 24–27, rejects conflicting support. A malformed signal when every available
  claim is conflicting has no valid nonempty selection. Authorization still
  chooses `signal_selection` at lines 137–140.

These source counterexamples do not require predicting model behavior. The fixed
eligible sets make the requested mechanical outcome impossible. They establish
that a signal-only or mixed-kind-only correction would be incomplete.

**Owning correction:** native validators retain compatibility, eligible-choice and
coverage facts. Authorization consumes them to choose an already approved
independent target, or returns the existing precise block before provider dispatch.
Where selection can safely change independently, use the existing selection unit
and revalidate its full dependencies. An empty admissible set cannot be solved
by inventing support, deleting a meaningful conflict or widening to the whole graph.

This requires checks for mechanically known impossibility, not a general solver
or proof that an LLM can find good prose. Semantic quality still requires proposal,
validation/review and live evidence. G1 remains the boundary for an unestablished
survivor choice or coupled write. Rollout: 08–10.

#### F2 — Immutable dependencies are retained internally but missing from requests

**Effect:** safe write isolation coexists with inadequate read context. A fake
provider can return a correct value using fixture knowledge unavailable to the
actual model.

[Specification candidate context](../src/domain/specification_candidate_context.zig),
lines 8–25, captures the current candidate and dependencies for CAS. But
[specification repair packet](../src/domain/specification_repair.zig), lines 52–67,
uses [session packet](../src/domain/specification_session.zig), lines 60–68, which
contains source evidence and the previously accepted brief, not the rejected
current candidate. [Atomic packet](../src/domain/atomic_repair.zig), lines 84–92,
adds target/rule/expected replacement only.

Consequently:

- A provenance repair receives the bad claim IDs without the unchanged business
  field or record fields those IDs must support.
- A value repair receives the bad value without its unchanged provenance, which
  controls eligible exact tokens and scoped passive references.
- During initial brief generation, the accepted brief is `null`; it cannot supply
  the missing rejected description incidentally.

The same failure class exists in extraction. In
[reference_extraction_repair.zig](../src/domain/reference_extraction_repair.zig),
line 48 returns the classification packet before projecting the current chunk
outcome. [Classification validation](../src/domain/token_classification_validation.zig),
line 67, forbids `preserve` under unchanged `no_feature_claim`. If a classification
is missing, the request lists the missing ID but omits that frozen outcome and
its restricted choices; the selected schema permits both decision variants.
Citation repair at lines 49–61 already projects the unchanged claim correctly.

**Owning correction:** domain packet builders project minimal immutable dependent
content from the existing authorization-bound candidate. The narrow response
schema remains narrow. Choices/restrictions derive from the native owner, not a
second prompt table. A record sharing provenance may require several unchanged
fields as read context; that does not authorize changing those fields.
Rollout: shared requirement in 08, specification in 11, classification in 12.

#### F3 — Guidance independently narrows or omits valid contract choices

[reference_model_input.zig](../src/domain/reference_model_input.zig), lines 77–84,
selects applicable constraint IDs separately from validation. Summary guidance
contains `matching_claim_content` and `exact_selected_token`; global guidance
omits them even though global signal validation enforces both. Rule descriptions
are shared, but applicability is independently maintained and has already drifted.

[specification_repair.zig](../src/domain/specification_repair.zig), line 41, says an
exact-copy repair must select a preserved token supported by unchanged provenance.
The selected response type is the broader `BusinessValue` union.
[specification_provenance.zig](../src/domain/specification_provenance.zig), lines
72–90, also permits normalized business text. If the unchanged provenance contains
only ordinary claims, the instruction demands a nonexistent token choice while
the native contract still permits normalized text. This is impossible guidance,
not proof that the replacement target itself is impossible.

Specification packet generation also independently filters retained claims at
`specification_session.zig:53–55`, while provenance enforces retained eligibility
at `specification_provenance.zig:40–48`. Those currently agree; this is a drift
risk, not an additional demonstrated mismatch.

**Owning correction:** applicable rules and eligible alternatives come from the
contract that validates them, then feed initial guidance, rejection and repair.
Keep text/schema rendering separate from rule ownership. Do not add a third
compatibility table to an authorizer or repeat constraints throughout YAML.
Rollout: 08–11, with the shared consumer audit in 12.

The shared [repair prompt](../design/workflows/spec/repair.prompt.md), line 2,
also says “Correct repair.rule”, although the rule is immutable input. Clarify
that the replacement must satisfy the rule. R15 does not prove this wording
caused the model to echo the repair envelope; changing it alone cannot cure F1.

#### F4 — Redundancy decisions disagree with canonical equivalence

[typed_text.zig](../src/domain/typed_text.zig), lines 96–114, joins adjacent literal
nodes and normalizes text. Summary/signal/conflict validation uses that canonical
representation. Reconciliation authorization instead compares raw native JSON
at [reference_reconciliation_repair.zig](../src/domain/reference_reconciliation_repair.zig),
lines 71, 84, 134, 155 and 183–186.

Two statements with identical claim IDs and otherwise identical content can
represent the same sentence as one literal or two adjacent literals. Both have
the same canonical text and evidence. Raw equality fails and overlapping entries
become `competing_entries` instead of mechanically redundant occurrences. Signals
and conflict summaries have the same representation-dependent comparison.

**Effect:** conservative blocking of an equivalent representation, not unsafe
acceptance. Nevertheless, the repair decision independently defines equivalence
and is brittle under permitted LLM variation.

**Owning correction:** retain canonical equivalence and coverage facts from the
owning validator and consume those in deletion authorization. Text equality alone
is insufficient: different evidence, obligations or meanings must still block.
Specification duplicate handling already uses normalized content/evidence facts.
**Keep atomic old-value/dependency equality exact**; normalizing `atomic.equal`
would weaken the correct CAS boundary. Rollout: 08–10.

#### F9 — Dependency binding depends on a lossy presentation and partial fact copies

**Final-review finding.** This differs from F2: F2 concerns information hidden
from the model; F9 concerns validation inputs missing from the engine's own
authorization preconditions.

[specification_candidate_context.zig](../src/domain/specification_candidate_context.zig),
lines 6–24, calls `session.packet`, copies its serialized model input into
`Facts.input`, then snapshots those bytes plus selected policy fields and candidate
state. Building a dependency binding therefore performs model-packet construction;
repair packet construction later performs it again. A presentation-only change
can affect authorization identity even when native validation inputs are unchanged.
More importantly, a lossy projection is not a complete validation dependency set.

Two source-derived fault-injection cases establish missing inputs:

1. Change only `context.registry.grammar.reference_names[0].basename` after a
   valid rejection, preserving source paths, policy rules, passive records and
   candidate. Specification packet projection does not read that field, so its
   snapshot remains unchanged. Yet
   [path_token_grammar.validateBinding](../src/domain/path_token_grammar.zig),
   lines 34–40, rejects it before candidate text validation.
2. With `summary_count > 0`, change only reconciliation progress's `latest` to
   `null`. The specification snapshot does not retain the summary chain and
   its model packet is unchanged. But
   [specification_provenance.bind](../src/domain/specification_provenance.zig),
   lines 22–27, calls the owning history validator, which rejects the broken chain.

The same fields are missing from
[specification_coverage_repair.Facts](../src/domain/specification_coverage_repair.zig),
lines 11–36. Its precondition can also remain unchanged before merge's native
revalidation detects invalid context. Extraction text facts retain reference
names, and reconciliation facts retain names and summary history:
[extraction context](../src/domain/reference_extraction_context.zig), lines 12–22;
[reconciliation context](../src/domain/reference_reconciliation_context.zig),
lines 5–41. These sibling differences demonstrate drift in independently authored
dependency projections. They do not justify copying an entire runtime context.

**Effect and limit:** under these domain-boundary mutations, authorization can
accept an unchanged snapshot even though context no longer satisfies its validator.
Failure may surface only after a repair call or at revalidation. These are source
counterexamples, not executed regressions or evidence of an ordinary live mutable
context exploit. The runner's immutable value ownership and subsequent validation
still matter; no successful invalid publication was demonstrated.

**Owning correction:** dependency capture consumes typed native evidence, lineage
and text-policy facts. The existing owners supply complete serializable facts
for the checks they perform; affected consumers reuse those projections.
Snapshotting and model-input rendering are separate consumers of those facts.
Keep process-local capability/current-policy identity checks at their existing
boundaries; never serialize ports, pointers or an entire runtime service object.

Remove `Facts.input` and dependency capture's call to `session.packet` once typed
capture replaces them. Replace the duplicated partial text-fact projections at
all affected consumers in the same change. Do not merely append the two observed
fields, hash a larger prompt, weaken exact CAS or create a new dependency registry.
Trace all actual validator reads, including lineage, before choosing the complete
projection. This is shared chunk 08 work with specification consumers 11–12.

### 4. Downstream interfaces that remain unfinished

#### F5 — Review evidence eligibility conflicts with reconciliation obligations

[Signal validation](../src/actions/reference/validate_reference_signal_proposals.zig),

The test deliberately records the incomplete downstream behavior; it is not a
