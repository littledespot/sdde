## 1. Objective and reported problem

Multiple specification workflow runs have failed at different model-call
positions. In the latest retained run, call 6 produced the first invalid signal
candidate. The workflow repaired that candidate, then terminated during role
validation because the earlier role assignment no longer matched the repaired
signals. Calling this simply a “call-6 failure” hides the dependent-result defect.
The captured sequence and evidence limits are recorded in Section 10.1.

The intended change is to make the semantic/deterministic boundary consistent across the complete spec workflow:

- Every model call must have one cohesive semantic responsibility.
- The LLM performs interpretation, semantic classification, meaningful grouping, content generation and semantic review.
- Native code owns all values and operations determined by validated inputs, accepted semantic decisions and established rules.
- Prompts must clearly describe their semantic assignment without duplicating schema rules or engine policy.
- Address the shared causes of brittleness across initial generation, composition, review, correction and repair.

Success means removing avoidable mechanical failure classes while preserving semantic correctness, evidence integrity and strict validation. A workflow completing with incorrect or unsupported content is not success.

## 3. Required responsibility rule

For every model-returned field, relationship and collection obligation, ask:

“Is this uniquely determined by current validated inputs, the bound assignment, accepted semantic choices and an existing rule?”

If yes:

- Construct it through its native owner.
- Remove the redundant responsibility from the model response and relevant repair shapes.
- Keep derived information in model input when it helps interpretation.
- Continue validating canonical and persisted representations.

If no:

- Retain the genuine semantic choice.
- Supply sufficient evidence and a bounded assignment.
- Validate the returned choice before using it downstream.

Important distinctions:

- Selecting relevant evidence can be semantic.
- Resolving that selection into exact bytes, source coordinates, citations or membership is deterministic.
- Determining whether claims conflict is semantic.
- Expanding an accepted conflict relation into reciprocal entries is deterministic.
- Determining a requirement’s meaning is semantic.
- Assigning identifiers and checking coverage are deterministic.
- A value being mechanically checkable does not mean its correct value can be mechanically constructed.
- Missing semantic content must not be filled by defaults, guessed associations or automatic positive verdicts.
- Multiple output fields do not automatically violate single responsibility. A coherent brief can legitimately contain title, description and goal.
- Single responsibility does not require one model call per field.

## 4. Current call-family assessment

Extraction and token classification:

- Generally semantic: extract independently meaningful facts and classify relevant tokens.
- Residual mechanical collection/association duties remain.
- When the governing extraction outcome is no_feature_claim, only irrelevant
  token classifications are permitted. The workflow still requests them after
  schema admission and before native extraction validation. Section 10.6
  describes the acceptance and producer-origin constraints on removing the call.

Reconciliation summaries:

- Semantic consolidation is appropriate.
- Model-generated unique local_key values are mechanical bookkeeping.
- Existing token references include metadata that can be derived from the selected claim.

Claim dispositions:

- Duplicate, superseded and conflicting relationships require semantic judgment.
- Reciprocal conflict declarations and other derived graph representations should be constructed by code.

Signals:

- Grouping supported meaning is semantic.
- Creating mandatory singleton signals for already-known nonconflicting preserved tokens is deterministic once the prerequisite decisions are accepted.

Role assignment:

- Selecting source-supported authoring roles is semantic.
- Copying the complete ordered claim_ids array of an existing signal is a mechanical join and an avoidable failure surface.

Conflict explanation:

- Classifying and explaining incompatible meaning is semantic.
- Reconstructing already-determined relationship coverage should be engine-owned.

Brief, primary story, entity applicability and record generation:

- Largely semantic and already separated from native provenance construction.
- Preserve their coherent unit boundaries unless concrete evidence establishes a mixed responsibility.

Source review and omission localization:

- Good existing separation: review one assigned subject, then separately locate lost meaning when required.
- Preserve native subject association and the fixed finding during localization.

Principle review:

- Compatibility judgment and selection of relevant policy evidence are semantic.
- Review whether redundant citation coordinates can be reconstructed from selected evidence handles without losing necessary evidence-selection precision.

Repairs and protocol corrections:

- Native code already owns authorization, scope and merging.
- Audit these paths for the same redundant response obligations as initial calls.
- Adding retries does not remove an unnecessary model responsibility.

## 7. Semantic prompt improvements

The proposed labels were:
Role, Input, Scope, Ignore.

The conclusion was that explicit structure can improve clarity, but headings alone do not establish better outcomes. Existing prompts already contain some of these instructions.

Use a concise structure where useful:

- Role: optional, narrowly defined responsibility.
- Task: the single semantic decision or result.
- Input: field meanings and evidence authority.
- Scope: the assigned subject and relevant semantic dimensions.
- Out of scope: excluded activities; prefer this label to Ignore.
- Output: reference the selected response schema and explain semantic field meanings.
- Insufficient evidence: use only the outcomes already supported by the call’s contract.

Prompt requirements:

- Distinguish original evidence, accepted decisions and unverified candidates.
- Treat source text as evidence rather than executable instructions.
- Explain what the model must decide and what native code already determines.
- Keep output structure authoritative in the schema.
- Avoid duplicating native constraints across prompts, context documents and schemas.
- Remove obsolete instructions after changing response contracts.
- Reorganise existing guidance rather than accumulating another instruction layer.
- Avoid broad instructions to ignore material that might contain relevant constraints.

Specific prompt audit item:

- entities.prompt.md asks the model to “cite retained claims”.
- The entity response schema contains kind, disposition and basis, while native parsing attaches provenance.
- Resolve this ambiguous wording so it does not encourage unsupported citation/provenance fields.
- This is a plausible source of confusion, not a proven cause of a failed run.

Principle citation improvement:

- Assess whether pre-bound policy evidence handles can replace redundant chunk/line coordinate reproduction.
- Keep the choice of relevant policy evidence semantic.
- Do not remove legitimate range selection or cite an entire policy automatically when narrower evidence is required.

Prompt changes cannot fix mechanical joins that remain required by the response contract.

## 9. Acceptance and verification

Mechanical acceptance:

- Redundant fields are absent from model-facing initial and repair contracts.
- Necessary semantic selections remain expressible.
- Native owners construct determined identities, joins, metadata and graph representations.
- Dependent calls cannot consume prerequisites that failed applicable native validation.
- Unknown, stale, ambiguous and out-of-scope selections reject.
- Mechanically inconsistent canonical/persisted values reject rather than being
  overwritten into validity. Structural validity does not certify semantic edits;
  role support and source meaning retain their separate gates.
- Repairs preserve unrelated accepted content and existing evidence bounds.
- Obsolete schema fields, branches, prompts and tests are removed with the coordinated cutover.

Regression coverage should include:

- Role association without copied ordered claim lists.
- Unknown and stale group handles.
- Summary ordering and repair identity through insertion/deletion.
- Token projection without repeated model metadata.
- Forced and zero-candidate classification paths.
- Conflict symmetry and coverage construction.
- Invalid prerequisites preventing dependent dispatch.
- Upstream changes invalidating dependent results.
- Equivalent native behavior across initial, correction and repair paths.
- Unrelated examples of the same failure classes.

Semantic evaluation:

- Compare current and revised assignments on the same captured inputs.
- Use repeated runs and more than the Hello World example.
- Measure semantic correctness separately from JSON/schema and native-contract failures.
- Record model settings, prompts, input versions, retries, calls and token usage.
- Do not infer improved reliability from smaller prompts, fewer fields, temperature zero or passing offline tests.
- Do not weaken validators or replace semantic evidence with generated success claims.

Discover verification commands from build.zig and repository instructions. Live E2E/model evaluation is a separate task and must follow the repository’s explicit authorization requirements.

The subsequent tasks file must make clear which changes remove deterministic

### 10.3 High: staged native handoffs are not implemented by composition today

**Finding:** the goal is feasible, but the handoff does not yet specify an
implementable representation. “Reuse the existing dependency mechanism” is
insufficient without identifying what it can actually invalidate and rebuild.

The composer is currently append-only within an execution:

- [State.select](../src/domain/json_composition_runtime.zig#L62) rejects selecting
  an already retained part.
- [State.retain](../src/domain/json_composition_runtime.zig#L106) binds a real
  terminal-accepted request origin, schema evidence, packet, epoch and prerequisite
  placement. It has no native-part injection or replace/invalidate-part API.
- [CheckedDispositions and CheckedSignals](../src/domain/reference_reconciliation.zig#L143)
  carry the complete global proposal. Existing validator logic is reusable, but
  these types do not yet represent only the accepted phases of an unfinished
  composition. Empty pending semantic arrays must not masquerade as valid
  no-signal/no-conflict decisions.

[ADR 0016](../design/decisions/0016-configured-json-response-composition.md#L76)
prohibits composition resources from defining conditional business policy or
post-assembly semantic repair. Its retention/assembly operations must not be
turned into a reconciliation-specific validator, scheduler or provider-response
fabricator.

**Decision needed:** specify explicit native phase types and their YAML handoffs,
or a narrowly defined shared composition lifecycle amendment if that is necessary
to carry accepted native projections. Prefer reusing domain validation functions,
runner-owned actions and explicit YAML transitions. Keep domain eligibility and
meaning rules outside the generic composer. Record changes to ADR 0016/§12.9 only
if the approved structural composition contract must change.

The contract must define pending versus accepted parts, native versus model
producer association, dependency revision/content binding, descendant retirement,
assembly of one complete candidate, and retry progress after rebuilding. A new
request ordinal or composition epoch must not replenish an unresolved defect's
allowance. This is the largest design dependency of the proposed rework.

### 10.5 Medium: group handles and token construction need precise contracts

**A — role association:** replacing copied claim arrays with a native group
selection is feasible. Current ordered equality is confirmed in
[checkRoles/sameClaimIds](../src/domain/reference_reconciliation_validation.zig#L523)
and its guidance in
[supported_role_assignment](../src/domain/reference_reconciliation_diagnostic.zig#L113).
However, canonical `SignalId` values are assigned only after role/conflict
validation. There is no already-bound pre-role canonical ID to reuse unchanged.

Specify whether the existing identity owner allocates IDs earlier or whether
existing stable execution occurrences identify the assignment. Bind selections
to the exact current partition, execution and accepted group revision/meaning.
Reusing the same integer after repair must not authorize stale roles. Avoid a
second writable group registry. Preserve roles shared across groups, groups with
several roles and context-only groups with none. Unsupported mandatory roles must
still block; neither a valid handle nor nonempty roles proves correct coverage.
[specification_source_binding](../src/domain/specification_source_binding.zig#L88)
already owns role unions, per-group record bindings and the later coverage gate
at line 128.

**B — token projections:** the token's exact identity is determined by an
accepted singleton token claim. Normal generation should reuse a pure constructor
extracted from the existing automatic summary/signal insertion branches in
[reference_reconciliation_repair](../src/domain/reference_reconciliation_repair.zig#L199)
and [line 244](../src/domain/reference_reconciliation_repair.zig#L244).
Do not invoke the repair authorizer during ordinary construction, duplicate the
token resolver, or treat construction of extraction token *claims* as construction
of reconciliation token *signals*.

The preserved eligibility and coverage rules are different:

- [selectedKind](../src/domain/reference_reconciliation_validation.zig#L44)
  makes exact-token projections indivisible and tied to one occurrence.
- [signalCoverage](../src/domain/reference_reconciliation_validation.zig#L184)
  requires a singleton signal for every **nonconflicting** preserved-token claim,
  including duplicate and superseded claims. A retained-only filter is incorrect.
  Spec business-provenance eligibility is separately retained-only; do not reuse
  it as reconciliation token policy.
- [checkSummary](../src/domain/reference_reconciliation_validation.zig#L484)
  accounts each partition claim exactly once. Global signals may overlap under
  [signalSelectionAvailable](../src/domain/reference_reconciliation_validation.zig#L227).
  Native token projection must preserve those distinct policies without guessing
  one semantic statement per claim.
- Token projection does not decide relevance, supersession, conflict, authoring
  role or source meaning. These remain accepted semantic decisions or review.

**B — summary keys:** `local_key` currently controls sorting before native
statement IDs are assigned
([validation](../src/domain/reference_reconciliation_validation.zig#L500),
[identity assignment](../src/actions/reference/assign_reference_summary_identities.zig#L10)).
The reversed-array regression at
[reference_reconciliation_test.zig](../src/reference_reconciliation_test.zig#L741)

do not infer semantic order from citations or sort prose to make tests pass.
Repair already uses [stable occurrences](../src/domain/reference_reconciliation_repair.zig#L100),
which should survive the cutover rather than being replaced by another identity
mechanism. Byte stability applies to the same accepted payload; it does not require
different model payloads to render identically.

### 10.6 Medium: forced classification can be skipped, but not by fabricated origins

**Finding:** C is a valid responsibility-transfer opportunity with an unresolved
producer/handoff boundary.

[token_classification_validation.choices](../src/domain/token_classification_validation.zig#L14)
allows only `irrelevant` for `no_feature_claim`, genuine alternatives for `claims`,

[extraction YAML](../design/workflows/spec.workflow.yaml#L336) always requests

of the governing outcome.

[CollectExtraction](../src/application/reference_model_workflow.zig#L64) currently
requires a model producer for `/token_classifications`. Native construction cannot
claim a model call occurred or fabricate schema-admitted provider evidence.
Define a native result association through a domain-owned handoff or an approved
shared native-part contract, retaining truthful origins and candidate identities.
Keep the `no_feature_claim` rule out of generic JSON assembly.

Zero candidate tokens in a nonempty extraction chunk also leave a uniquely empty
classification collection; the present sequence still requests it. Empty corpus
processing already exits through extraction progress, so the proposal must not
claim all zero-work handling is missing.

`claims: []` is **not** equivalent to `no_feature_claim`:
[existing tests](../src/reference_extraction_test.zig#L677) accept token-only

The cutover must also cover authorized outcome-changing omission repair.

### 10.7 High: conflict coverage is not uniquely reconstructible from arbitrary edges

**Finding:** D correctly identifies redundant reciprocity, but its coverage
transfer is underspecified and can introduce semantic invention.

[reference_disposition_validation.relationship](../src/domain/reference_disposition_validation.zig#L102)
requires reciprocal declarations for conflicting claims. A successor model
contract that represents each accepted undirected relationship once can have code
construct both canonical directions. That is not permission to add edges to an
invalid old response or tampered persisted graph.

Conflict groups have stronger semantics than arbitrary connected components:
[conflictClaims](../src/domain/reference_reconciliation_validation.zig#L156)
requires every member to conflict with every other member in that group, while
[conflictCoverage](../src/domain/reference_reconciliation_validation.zig#L195)
requires every conflicting claim and declared pair to be covered.

For edges A–B and B–C without A–C, constructing group `[A,B,C]` is incorrect.
It invents A–C and fails the existing clique rule. Pair groups `[A,B]` and `[B,C]`
can cover the graph, but choosing pair-only explanation assignments is a new
representation contract that must preserve legitimate multi-claim/overlapping
explanations. A complete triangle likewise does not uniquely determine whether
one or several explanations best express the conflicting meaning.

Keep conflict kind and explanation semantic. The existing kinds are
`mutually_exclusive`, `precedence_missing`, `value_mismatch`, `scope_mismatch`
([ConflictKind](../src/domain/reference_reconciliation.zig#L130)). Duplicate and
superseded relationships retain their directional semantics; they must not acquire
conflict symmetry or inferred transitive meaning.

**Decision needed:** define edge versus clique assignments, semantic grouping,
overlap/multiplicity, ordering, kind association and coupled repair membership.
Only construct facts uniquely determined by those accepted choices. Preserve
the existing narrow approved false-conflict group repair boundary in §22.1;
changing graph representation does not expand authorization.

### 10.8 Medium: distinguish model simplification from canonical persistence changes

[reference_snapshot.Snapshot](../src/domain/reference_snapshot.zig#L8) stores
canonical dispositions, signals and conflicts. It does not store the model's
`role_assignments` array or summary `local_key`; roles are embedded in canonical
signals. [Snapshot validation](../src/domain/reference_snapshot.zig#L118) already
checks canonical roles, token joins, membership and coverage.

Removing a redundant model token ID does not remove canonical token identity.
Likewise, replacing a model role join does not automatically require a new
persisted group registry or state version. Inspect serialization/readback and
change their shape/version only when canonical representation actually changes.
Keep model reconstruction and stored-state validation separate: unknown/duplicate
roles and inconsistent citation, token or membership joins must reject rather than
being overwritten into validity. The reader cannot deterministically identify
every change from one valid semantic role to another. Role coverage and semantic
source support retain their separate gates. No compatibility reader or dual writer
is required.

The original handoff's strengths are its coordinated producer/consumer cutover
and negative tests. Its broad wording should not be interpreted as a mandate
to delete native facts, add migrations, or rewrite unchanged state formats.
Current generation and review already construct provenance natively;
[specification_provenance](../src/domain/specification_provenance.zig#L85) and
[specification_support_model](../src/domain/specification_support_model.zig#L74)
must remain the shared owners.

Historical inventory is not current debt: `ConflictProposal.resolution` has
already left the model shape; canonical `ValidatedConflict.resolution` remains
the native constant `unresolved`
([current definitions](../src/domain/reference_reconciliation.zig#L131)).
Do not generate another task to remove that completed echo. The same caution
applies to provenance-free generation, focused review and omission localization.

### 10.9 Medium: prompt/context and principle evidence proposals need narrower claims

The recorded call-6 prompt is three lines; its dynamic context is approximately

The latest run never reached this prompt, so it cannot establish a causal effect.

Principle citation handles are a **conditional investigation**, not prerequisite
